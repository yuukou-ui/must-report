# 清掃報告書ツール — AIへの引き継ぎ書

このファイルは、このリポジトリで働くAI（Claude Code）が毎回いちばん最初に読む「職務記述書」です。
AIのセッションは毎回まっさらな状態から始まり、前回の会話を何も覚えていません。
次のAIが同じ説明を受け直さなくて済むように、分かったことはすべてこのフォルダ（`.claude/`）に書いて貯めていきます。
（ユーザーは「AIのためにコンテキストを貯める」「AIを社員として育てる」という考え方でこのリポジトリを運用している）

## この仕事について
- マスト管理 有限会社（建物の清掃）の、清掃報告書まわりの社内ツール。
  ビルドの無い静的サイトで、`main` ブランチが GitHub Pages でそのまま公開されている＝ `main` に入った変更は即、本番。
- 毎日の流れ：
  1. 現場の清掃者がスマホ（iPhone・Android）で **報告書ツール**（`index.html`）を開き、物件名・清掃日・清掃者・作業内容・特記事項・写真（最大8枚）を入れて A4 1枚のPDFを作り、LINEで送る。電波の無い建物でも使える。
  2. 事務所がPC（Chrome/Edge）で **まとめツール**（`matome/index.html`）に届いたPDFをまとめて入れ、取引先ごと・提出の区切り（前半分／後半分／月分／月1回）ごとに1つのPDFへ結合して保存し、取引先へ提出する。
- 物件はおよそ2週間で一回りする運用。物件ごとに月2回・月1回の違いがある。
- ユーザー（このリポジトリの持ち主）はエンジニアではない。説明・コード内コメント・コミットメッセージは、専門用語を避けた日本語で書く。
  どちらを選んでも何かを失う場面（例：LINEに余分な1通が届く vs. LINEで送れない）では、AIが勝手に決めず、違いを平易に説明してユーザーに選んでもらう。

## ファイルの地図
| パス | 中身 |
|---|---|
| `index.html` | 報告書ツール本番（スマホ用・ホーム画面名「取引先別_清掃報告書」） |
| `sw.js` | 報告書ツールのオフライン用の保管係。画面本体はネットワーク優先、部品・画像はキャッシュ優先。まとめツールは対象外 |
| `lib/` | html2canvas・jsPDF を自前で置いている（圏外でもPDFを作るため。CDNに戻さない） |
| `manifest.webmanifest`, `icon*`, `favicon-32.png` | 報告書ツールのホーム画面アプリ設定とアイコン |
| `matome/index.html` | まとめツール本番（PC用・ホーム画面名「報告書PDF結合」）。pdf-lib・pdf.js は jsDelivr のCDNから読む |
| `matome/*-v2.*` | まとめツールのアイコン類。iOSの古いキャッシュを避けるため名前に `-v2` を付けてある |
| `preview/`, `matome/preview/` | 実機確認用の検証ページ（上部に「検証用ページ（本番ではありません）」の帯）。本番の古い写しで、同期はしていない |
| `.claude/` | AIへの引き継ぎ（このファイルと `context/`）。サイトには出ないが、リポジトリが公開なのでGitHub上では誰でも読める |

## 必ず守ること
1. **リポジトリは公開されている。** 物件名の一覧・取引先名・人の名前・連絡先などを、コード・引き継ぎ書・コミットメッセージのどこにも書かない。
   物件一覧を公開URLに置かず、LINEで文字列を渡す方式にしているのもこのため。
2. **現場が毎日使っている本番に直結している。** 壊れた状態で `main` に入れない。作業は指示されたブランチで行う。
3. **両ツールで同じ決まりを使っている所は、片方だけ変えない。**
   - 物件名の照合キー `normKey`（全角半角・空白・ハイフン・ひらがな/カタカナ・番号の書き分け V=Ⅴ=五=5）。両ファイルにまったく同じ関数がある。
   - 物件一覧の文字列形式（1行目 `MUST-BUKKEN/1 <件数>`、2行目から1行1物件）。
   - 報告書PDFの内部情報（subject＝清掃日 `YYYYMMDD`、keywords＝物件名）。まとめツールはファイル名よりこちらを先に読む（LINEを通るとファイル名が変わることがあるため）。
4. **端末に保存しているデータ（localStorage）のキー名と形を、勝手に変えない。** 変えると現場の端末に貯まった履歴や登録が消えたように見える。
   形を変える時は古い形も読めるようにする（既存コードもそうしている）。キーの一覧は `context/glossary.md`。
5. **リポジトリ直下や公開フォルダに Markdown などの新しいファイルを置かない。** GitHub Pages（Jekyll）が変換して公開してしまい、
   書き方次第（`{{` `{%` など）ではサイト全体の更新が止まる。AI用のメモは `.claude/` の中だけに置く（`.` で始まるフォルダは公開されない）。
6. **スマホではエラーの中身が見えない。** 失敗は黙って捨てず、画面に言葉で出す（写真の取り込み・送信経路の表示など、既存の作りに合わせる）。
   色だけで知らせず言葉も添える（屋外の日差しや色の見分けにくさで見落とすため）。
7. **日付は日本時間で扱う**（`todayJST()` を使う）。`new Date()` や `valueAsDate` で日付を作ると、朝9時前に前日になる。

## 仕事の進め方
- 変更の前に、関係する `context/decisions.md` の項目を読む。過去に実機で確かめた結果を、知らずに覆さないため。
- 実機でしか分からない変更（共有シート・LINE・写真・iOSの癖など）は、まず検証用ページに入れてユーザーに実機で触ってもらい、確かめてから本番へ。
  検証用ページは本番より古いので、使う時は本番の今の中身を写してから変更を入れる。
- コード内のコメントは「何をしているか」より「なぜそうしているか」を書く。既存のコメントの書き方（平易な日本語・過去の経緯と日付）に合わせる。
- コミットメッセージ：1行目は `報告書ツール: ～` / `まとめツール: ～` / `両ツール: ～` の形で「何ができるようになったか」。
  2行目以降に、原因・対策・実機で確かめた結果・ユーザーが選んだ方針を書く（これも大事な引き継ぎになる）。
- 自動テストもビルドも無い。変更後は少なくとも、`<script>` の中身に構文エラーが無いことを確かめる。

## コンテキストを貯める（毎回の仕事の終わりに必ずやる）
AIは会話が終わると忘れる。仕事で分かったことは、その仕事のコミットに一緒に入れて残す。
- **`context/decisions.md`** … 決めたこと・実機で確かめた事実・不具合の本当の原因。「いつ・何を・なぜ・コミット」を1項目にして、いちばん上に足す。
- **`context/glossary.md`** … 新しい言葉・新しい保存データ（localStorage のキー）・新しいファイル名の決まりができたら足す。
- **このファイル** … 守るべき決まり、ユーザーの好みや進め方が新しく分かったら直す。
- 古くなった記述は、見つけたその場で消すか直す。間違った引き継ぎは、引き継ぎが無いより悪い。
- 書かないもの：公開して困る情報（「必ず守ること」の1）、コードを読めばすぐ分かること。
